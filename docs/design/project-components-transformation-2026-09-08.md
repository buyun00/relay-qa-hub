# QA Hub 项目制与组件化改造方案

版本 2.1  
修订日期 2026 年 9 月 9 日  
编制 Codex  
面向 项目负责人 开发 测试与运维  
适用 当前本机部署及后续多个内部项目共同使用

本方案将 QA Hub 改为只有项目一级的内部协作工具。人员可以加入一个或多个项目，普通员工只看到自己加入的项目；进入项目后继续按名字登录。系统只保留项目员工和一个 GM，GM 统一管理项目、人员归属及功能开关。

基础产品只负责 Bug 单管理。打包、单次打包上传、增量上传、Relay AI 制作、第三方订单同步等能力，分别作为组件按项目启用。HTTP API 与 MCP 共用业务实现，两种方式均能独立完成列表、详情、状态操作等工作。Android APK、Windows EXE 和 Web 使用同一套项目与组件配置，APK 与 EXE 纳入同一批开发和发布验收。

实现上复用现有 API、SQLite 数据模型和项目成员表，新版内部仍使用一套 API 服务与一个业务数据库。主要工作是解除固定项目假设、补齐项目切换和旁路数据归属、拆分组件，以及补全 HTTP API 与 MCP 对等能力。本文替代版本 1.0 中的工作室层级、多身份权限、邀请认证及每工作室独立服务方案。

版本 2.1 增加实施硬约束：在新的 Git 工作树中制作，新版以独立实例与当前主分支生产版本长期并行运行。代码、数据库、附件、队列、配置、端口、客户端身份和发布更新通道都必须分开。完成本任务不包含替换生产、合并主分支或升级日常客户端。制作完成后逐项真实操作覆盖全部功能，实施与验收细则见第 16 和第 17 节；与前文或既往默认发布习惯冲突时，以本条为准。

## 1 已确定的产品规则

### 1 1 本次修订的结论

| 事项 | 最终规则 | 对开发的影响 |
| --- | --- | --- |
| 组织层级 | 只有项目，不增加工作室层 | 复用 projects，不新建 studio 或 workspace 业务层 |
| 人员归属 | 一个人可分配到多个项目 | 复用 users 与 memberships，列表只返回所属项目 |
| 员工登录 | 选择或进入项目后按名字登录 | 保留姓名规则和会话机制，登录增加项目参数 |
| 身份 | 项目员工与一个 GM | 页面不再出现管理员、开发者、验收者等权限角色选择 |
| 人员管理 | 项目内维持当前使用方式 | 名单、关联、停用等操作仅影响当前项目 |
| 基础功能 | Bug 单管理及其必要配套 | 不依赖打包、上传、Relay 或外部订单服务 |
| 可选功能 | 每个项目独立启用组件 | 同一版本程序，服务端配置决定该项目可用能力 |
| 对外接口 | HTTP API 与 MCP 均提供 | 共用业务服务，界面能做的主要 Bug 操作同步开放 |
| 客户端 | APK、EXE 同步兼容 | 不以仅完成 Web 或 EXE 作为项目改造完成 |

这里仍需保留很少的项目归属检查：列表只读当前人员所属项目，修改时核对 Bug 属于请求中的项目，停用人员不能继续进入该项目。这些检查直接实现“看不到不属于他的项目”，不引入权限表达式、授权范围配置或多级角色系统。

### 1 2 姓名与业务责任字段

提交人、修复人、关闭人、验收负责人等继续是 Bug 上的业务字段，用来分工和追溯，不作为额外身份。项目员工按当前规则共享项目内管理能力，不重新增加“只有原提交人才能关闭”“只有修复人才能退回”等限制。

沿用可信内部姓名识别，不新增员工密码、短信、邀请审批、企业 SSO 或 OAuth 流程。姓名登录不核验现实中的本人身份；本方案的目标是内部人员分组、项目数据正确归属和操作简便。

## 2 现有代码基础与改造范围

本次设计依据本地源码检查，基线提交为 `62b4495c9b28dc3aea1d5633e870be4e1fdf841f`。下文将“当前已有”和“建议新增”分别说明；接口样例、组件键和新增表结构均是待实现设计。

### 2 1 可以直接复用的能力

数据库已有账号、项目、人员、项目成员关系；项目目录查询已经通过有效成员关系筛选可见项目。Bug 单具有状态、修复轮次、人工完成、验收、评论、附件、事件、版本检查和删除留痕等基础。Android 的本地仓库参数也已经包含项目标识。

现有登录支持姓名，Web 使用会话，原生客户端可以取得令牌。HTTP API 已经覆盖较多 Bug 操作；EXE 内置 MCP 已有项目列表、Bug 列表、上下文、评论、开始修复、提交修复及附件落盘等工具。以上都应保留并改造，避免重新建立一套 Bug 系统。

### 2 2 真正需要修改的部分

| 领域 | 当前情况 | 需要完成 |
| --- | --- | --- |
| API 启动 | main.ts 仍使用固定 MOBILE_SCOPE 装配多项存储与登录服务 | 项目来自明确请求参数或已绑定的项目会话，不能继续固定到原项目 |
| 数据访问 | 部分存储先检查是否等于固定项目，创建也用固定值 | 改为支持动态项目，复用成员关系和记录归属检查 |
| 登录与入口 | 姓名登录主要服务当前固定项目 | 增加项目入口、项目参数和所属项目切换 |
| 打包 | Jenkins 服务包含固定任务和预设配置 | 抽为按项目配置的打包组件 |
| 上传 | 独立队列与快照缺少完整项目维度 | 命令、任务、历史、缓存、日志和凭据关联均记录项目 |
| Relay 制作 | 外部项目映射和部分生产状态文件存在全局假设 | 项目独立绑定与查询，关闭组件时不再自动执行 |
| 客户端缓存 | 部分草稿只按人员保存，部分设置是全局值 | 缓存、草稿、通知与请求都明确所属项目 |

已有 `accounts` 可作为本机部署内部的兼容字段保留，所有项目共用现有部署账号。界面、产品文档和管理流程不再出现账号下套工作室、工作室下套项目的层级。已有 `modules` 表表示 Bug 分类，与可选软件组件是两件事，不能混用。

## 3 项目入口与简单姓名登录

### 3 1 普通员工使用流程

1. GM 创建项目，并把项目入口链接、二维码或客户端连接配置发给该项目人员。
2. 员工打开入口，登录页明确显示项目名称，填写姓名即可进入。
3. 姓名按当前规范解析为人员记录；首次从该项目入口登录时，在该项目登记有效成员关系，不加入其他项目。
4. GM 也可以预先把已有人员分配到多个项目。登录后，项目切换列表只显示此人的有效所属项目。
5. 只有一个项目时直接进入，不额外要求再选一次；有多个项目时默认打开本次入口指定项目，之后可切换。
6. Bug、评论、附件和人工操作同时记录实际操作人员及所属项目。

不提供面向未登录员工的全项目目录。项目入口可包含项目 ID 或固定短码，用来确定登录到哪里，不增加邀请审批。按当前要求，内部发放项目入口即表示允许从该入口登记；若以后要求“知道其他项目入口也不能自行加入”，再把首次登记改为 GM 预分配即可，不应在本次默认加上复杂流程。

### 3 2 人员归属与停用

沿用现有稳定人员 ID 和姓名映射，同一已有人员可关联多个项目。登录不重建历史人员，不批量重算历史操作人的 ID。真正同名的不同人员使用可区分的登录名，按现有人员关联方式处理，不自动合并历史。

项目内的停用作用于该项目的成员关系。A 项目停用某人后，该人在 B 项目的记录和资格保持有效。被明确停用的项目关系不能在下一次姓名登录时自动恢复；由 GM 或当前项目内原有人员管理流程恢复。

人员列表、关联、解除关联、停用等现有入口继续保留，但所有项目内操作只改变该项目。涉及跨项目的全局身份合并由 GM 统一处理；项目内姓名显示或别名调整不能连带修改其他项目的历史归属。

### 3 3 唯一 GM

GM 只有一个固定账号，由服务端配置其稳定 ID。建议给 GM 单独保留一个简单管理口令；普通人员仍然只填姓名。不能因为员工输入的名字恰好为“gm”，就赋予全局管理能力。

GM 可以创建、停用和查看全部项目，分配人员所属项目，配置组件及外部连接，并查看项目运行记录。GM 在编辑 Bug、处理构建任务或查看项目人员时，也必须明确当前项目，避免把设置写入错误项目。

项目内不新增项目管理员身份。既有内部人员管理按原有操作习惯保留。GM 是唯一全局管理身份，外部脚本通常使用相应项目员工的姓名会话，不共享 GM 管理口令。

### 3 4 项目切换行为

切换时保存当前项目未提交草稿，取消或作废旧页面请求，重新加载新项目的 Bug、人员、分类、统计和组件配置。迟到的 A 项目请求不得覆盖 B 项目界面。

正在运行的后台任务继续属于创建它的项目，不随客户端切换而迁移。打开通知、附件、深链或 MCP 结果时，使用记录中的项目 ID 定位；若已经被移出该项目，提示不可访问并刷新项目列表。

## 4 目标架构

### 4 1 保持一套服务和一个业务数据库

```text
Web                 Windows EXE             Android APK
          同一套项目目录与组件配置
                         |
HTTP API 入口       服务端 MCP 入口       EXE 本地 MCP 入口
                         |
           共用项目与 Bug 业务服务
                         |
Bug 管理基础模块     按项目启用的组件模块
                         |
       现有 SQLite 数据库与项目文件目录
                         |
    按项目绑定 Jenkins 上传器 Relay 等外部服务
```

基础层负责项目、姓名会话、人员、Bug、评论、附件、操作记录和必要通知。组件层只承接额外工作流。业务服务统一处理状态变化和记录写入，HTTP 与 MCP 仅把不同调用形式转换成同一业务请求。

新版内部部署一套 API，不要求每个项目各自维护端口、数据库、安装包和服务实例。开发及并行运行期间，新版与旧生产各自拥有独立 API 实例和独立数据库，不共用运行目录。组件可以先作为代码库内的独立模块，不需要第一期引入插件市场、动态安装或独立微服务。原有外部平台只有在独立测试任务和资源可用时才接入新版，不能复用正在生产作业的工作区或发布目标。

### 4 2 项目数据如何互不串用

所有项目业务数据使用明确的 projectId。请求先确认操作者属于项目，再读取或修改该项目记录；GM 可操作全部项目。一个公共入口完成这两步，业务代码不用重复实现一套复杂权限框架。

附件、任务日志、构建记录、上传命令、下载链接、Relay 映射、通知和本地缓存都要带项目归属。只在 Bug 列表加过滤不够，否则列表虽然隔开，附件下载或后台队列仍可能串项目。

新文件建议使用 `data/projects/{projectId}/...`。历史附件继续使用原路径和索引，读取时通过数据库归属定位，不必为了目录整齐立即搬迁全部历史文件。路径中的项目名只用于显示，稳定 ID 才用于索引和目录。

### 4 3 共用机器的运行边界

不同项目的任务使用独立工作目录、产物目录、上传目标和必要配置；共享构建资源由现有队列串行或限并发执行，避免两个任务同时改同一份工作区。组件任务较重时，后台执行不能阻塞 Bug API 请求。

同一台机器、同一数据库仍然共用硬件容量和宿主机故障范围。这里的“互不影响”首先指业务数据和配置不串用；共享机器上的排队与停机不会因项目分组自动消失。初期使用简单队列和并发上限即可，不增加配额套餐、计费或复杂调度平台。

## 5 数据模型与存储改动

### 5 1 优先复用现有表

| 数据对象 | 处理方式 | 核心规则 |
| --- | --- | --- |
| accounts | 保留现有内部记录 | 作为本机兼容字段，不变成产品层级 |
| projects | 直接复用并补齐管理操作 | 稳定项目 ID、名称、启用状态 |
| users | 复用稳定人员 ID 与姓名映射 | 不重写历史人员 ID，不按项目复制全部人员档案 |
| memberships | 作为人员与项目的关系 | 可多项目，停用与恢复只作用于指定项目 |
| membership_roles | 兼容旧结构和调用 | 产品只认员工与 GM；旧角色不再产生多套员工权限 |
| bugs 等业务表 | 复用现有结构 | 查询、创建、修改都使用同一明确项目 |
| modules | 继续表示 Bug 分类 | 与组件设置分开管理 |
| 会话表 | 沿用现有会话和令牌存储 | 识别人员，记录登录项目；切换不能改变历史请求归属 |

如果现有业务服务仍要求某些角色标志，可在兼容适配处给项目员工统一映射所需能力，而不是继续让用户配置多种角色。具体表清理可后续进行，首期避免删除兼容字段引起历史流程回归。

### 5 2 少量新增项目配置

建议新增 `project_components`，唯一键为项目 ID 加组件键，字段包含 enabled、config、version、updatedBy、updatedAt。基础 Bug 管理固定存在，不需要给 GM 一个可以误关基础系统的开关。

外部连接可以保存在组件配置及现有凭据引用中；只有确实需要多条连接时再增加 `project_integrations`。客户端可读配置只包含名称、开关、可用状态和必要选项，Jenkins、上传器、Relay 的密码或令牌继续保存在服务端。

GM 身份优先采用服务端固定配置，不单独建设角色平台。操作日志复用当前事件与审计机制，对人员归属、组件开关、外部连接修改补充项目 ID、操作者和变更摘要即可。

### 5 3 队列与旁路文件

当前上传独立队列中的命令缺少项目列，快照会组合多个上传人的任务。这里必须同步补齐项目字段和查询条件。上传器的 `accountIdentity` 表示外部上传账号，不能拿来代替 QA Hub 的项目标识。

打包、上传、Relay 的任务 ID 必须连同项目归属一起保存。外部任务的回调、轮询和重试按原任务映射找到项目，不能用“最后一次在界面选中的项目”。项目切换、服务重启和 GM 同时查看多个项目都不能改变任务归属。

缓存键至少包含服务地址、项目 ID 和人员 ID；任务锁按实际共享资源确定，不能把必须全机串行的工作区锁错误拆成项目锁。文件下载和清理也从已登记任务归属出发，不能根据请求字符串直接访问任意路径。

## 6 Bug 管理基础模块

### 6 1 基础范围

基础模块包含 Bug 列表、检索、筛选、详情、创建、编辑、指派、评论、附件、历史、状态操作、人工修复完成、验收、关闭、退回与现有删除能力。项目人员、Bug 分类、必要的统计与通知属于它的配套功能。

已有截图、录屏或设备证据只要用于提交和查看 Bug，继续作为基础配套保留。独立的自动制作、构建发布和外部任务执行能力放入组件。关闭所有可选组件时，APK、EXE 仍然可以完整处理一个 Bug 从提交到关闭的流程。

### 6 2 状态变化保持现有含义

开始修复、提交修复、人工完成、验收通过、退回和关闭复用当前业务动作。人工完成表示已经交付处理结果并进入相应待验收流程，不等于直接通过验收；Relay 执行结束也不等于 Bug 已关闭。

项目员工可以通过界面、HTTP API 或 MCP 发起当前允许的明确动作，三种入口的条件与结果一致。接口提供状态操作能力，但不直接暴露任意改写数据库状态的通用开关。修复人、关闭人和验收负责人仍然负责记录分工，不增加独立权限身份。

关闭 Bug 不依赖打包组件、Relay 成功、构建产物或外部订单同步结果。第三方同步失败记录结果并允许重试，不阻塞 QA Hub 内部操作。删除继续保留现有可恢复、可审计的行为，普通列表、统计与 MCP 读取采用相同过滤。

### 6 3 并发和重复提交

沿用 expectedVersion 和现有幂等机制：界面与脚本同时改同一个 Bug 时，旧版本提交提示刷新；同一操作重复调用返回已执行结果，不能重复创建修复轮次或重复启动外部任务。这属于数据正确性，不需要用户配置任何权限策略。

## 7 HTTP API 与 MCP

### 7 1 两种入口均可独立使用

HTTP API 随 API 服务运行，其他系统可以直接调用，不要求先打开 EXE。服务端 MCP 与它共用业务服务，同样能够独立运行；保留现有 EXE 本地 MCP 兼容入口，用于本机工具接入和附件落盘。

普通自动化可以使用项目 ID 加姓名登录，取得与现有原生客户端方式一致的会话令牌，然后调用该人员所属项目。无需另外建设 API 角色、授权范围、OAuth 客户端或独立服务账号体系。会话到期按同一姓名流程重新登录即可。

本方案中的“对外”指提供给其他内部程序和系统调用，部署时公布实际可达的服务地址与接口文档。沿用当前连接方式，不把本地 127.0.0.1 的 EXE MCP 误写成其他机器可直接访问的服务地址。

### 7 2 现有能力与补齐范围

以下工具名中标注“新增”的是建议名称，开发时可保持当前命名风格。现有工具保持兼容，增加项目参数和一致的返回结构。

| 业务能力 | HTTP API | MCP |
| --- | --- | --- |
| 所属项目列表 | 已有项目目录，补齐多项目登录后的调用 | 现有 qa_list_projects |
| Bug 列表与筛选 | 现有 GET /api/v1/bugs，明确项目参数 | 现有 qa_list_bugs |
| 详情与上下文 | 现有详情、事件、评论、附件读取 | 现有 qa_get_bug_context |
| 创建与编辑 | 现有创建和 PATCH 能力，统一项目归属 | 新增 qa_create_bug、qa_update_bug |
| 开始修复 | 复用现有人工工作流动作 | 现有 qa_begin_fix |
| 提交修复 | 复用现有修复交付业务 | 现有 qa_submit_fix |
| 人工完成与状态操作 | 复用 complete、manual-complete、验收等路由 | 新增 qa_bug_action，包含明确动作名 |
| 添加评论 | 现有评论接口 | 现有 qa_add_comment |
| 上传与读取附件 | 保留现有附件上传、绑定和下载能力 | 补齐上传及绑定工具，保留 materialize 工具 |
| 删除 Bug | 现有 DELETE，复用版本检查和留痕 | 新增 qa_delete_bug |
| 人员 分类 统计 | 项目内现有能力逐项整理为公开接口 | 补齐对应查询与现有管理动作工具 |
| 可选组件操作 | 启用后提供该组件 API | 启用后提供同一组件工具或明确可用状态 |

当前 MCP 不能直接视为已经完整覆盖所有状态操作。新增工具必须与 HTTP 接口共用现有业务动作，尤其要覆盖人工完成、验收、关闭、退回和删除，避免最后仍需回到界面补做关键操作。

### 7 3 建议的统一接口约定

新规范优先使用 `/api/v1/projects/{projectId}/...` 表达项目。现有 `/api/v1/bugs/...` 保留兼容：带 Bug ID 的调用从记录确定项目并核对成员关系；列表、创建等没有具体记录的调用必须传项目或使用明确绑定到单项目的会话。

若一个调用存在多个可选项目而又没有明确项目，返回“请选择项目”，不随机选第一个。业务短编号只在项目内解释，自动化应优先使用稳定 Bug ID。客户端与 MCP 不得自行猜测当前项目。

建议新增统一业务动作入口，作为现有路由的共同适配层，而不是重写状态机：

```text
POST /api/v1/projects/{projectId}/bugs/{bugId}/actions

{
  "action": "manual_complete",
  "expectedVersion": 12,
  "note": "已人工修复，等待验收"
}

Idempotency-Key: client-generated-operation-id
```

对应 MCP 可使用同一组参数：

```json
{
  "tool": "qa_bug_action",
  "arguments": {
    "projectId": "project-a",
    "bugId": "stable-bug-id",
    "action": "manual_complete",
    "expectedVersion": 12,
    "note": "已人工修复，等待验收",
    "idempotencyKey": "client-generated-operation-id"
  }
}
```

上例为业务参数示意，不代表完整 MCP 协议报文。close、reject、manual_complete 等动作名与所需字段在开发时对齐当前状态机，并生成同一份动作清单，避免两端分别维护不同枚举。

### 7 4 最小调用流程

```text
1  从项目入口取得 projectId
2  使用项目姓名登录接口提交 projectId name client
3  使用返回的会话令牌调用项目列表或 Bug 列表
4  读取 Bug 当前 version
5  提交明确动作 expectedVersion 和幂等键
6  从响应取得最新状态 version 与操作记录标识
```

建议登录请求增加 `{projectId, name, client}`，保留现有 Web 会话和 Android 令牌返回习惯。接口文档必须给出真实实现后的登录 URL、请求头、上传示例、错误处理和 MCP 连接地址；本设计不把尚未实现的示例地址写成已可使用接口。

错误至少统一表达：项目不可访问、记录不存在或不属于该项目、组件未启用、参数错误、版本冲突、当前状态不允许动作、会话失效。API 的状态码和 MCP 的结构化错误应映射到同一业务错误，普通员工不获得其他项目记录的详情。

### 7 5 附件与组件工具的一致性

HTTP 下载返回文件内容或可访问下载地址，并包含文件名、类型和哈希等已有元数据。EXE 本地 `qa_materialize_attachment` 继续负责下载到调用方可用的本机路径；服务端 MCP 返回资源或下载地址，不能把服务端磁盘路径当成远端用户可直接打开的文件。

附件上传、Bug 绑定、评论和状态提交使用同一项目。API 与 MCP 的一致性是业务结果一致，本地文件落盘属于客户端差异，不要求远端 API 模拟 EXE 文件系统。

组件工具都显式接收项目，或使用已绑定的单项目上下文。多项目 MCP 会话可以保留工具目录并返回各项目的启用情况；无论工具是否显示，实际执行时都检查该项目开关。关闭组件后的旧脚本请求应明确失败，不能悄悄执行。

## 8 可选组件设计

### 8 1 第一批组件

| 组件 | 启用后提供 | 主要项目配置 |
| --- | --- | --- |
| 打包 build | 触发打包、查看队列、日志、结果与产物 | Jenkins 连接、任务、参数预设、产物位置 |
| 单次打包上传 build_upload.single | 一次触发指定构建并衔接一次上传 | 打包预设、上传目标、失败后重试方式 |
| 增量上传 upload.incremental | 选择已有产物或增量包上传，查看进度和历史 | 上传账号引用、目标平台、目录或频道 |
| Relay AI 制作 relay.production | 外部项目与任务列表、创建、继续、动作、批次 | Relay 地址、凭据引用、外部项目映射 |
| 第三方订单同步 qingyu.sync | 订单查询关联、同步状态与失败重试 | 对应第三方连接和项目映射 |

如果现有“打包上传”同时包含多个操作入口，界面可继续保留熟悉的分组，但底层分成打包能力、上传能力和单次串联流程。用户看到的名称可以沿用当前产品术语，组件键只用于实现。

增量上传与增量构建分开描述：上传组件支持传输指定增量产物，不自动代表 Unity 已经具备可靠的增量构建或更快打包。新增构建算法不作为项目制改造的隐含任务。

### 8 2 项目配置示例

| 项目 | 基础 Bug 管理 | 启用组件 |
| --- | --- | --- |
| 项目 A | 固定提供 | 打包、单次打包上传、增量上传、Relay AI 制作 |
| 项目 B | 固定提供 | 增量上传 |
| 项目 C | 固定提供 | 无，完整使用人工 Bug 流程 |

GM 打开项目设置，可以逐项启用组件并填写必要连接。基础 Bug 管理不受组件开关影响。配置保存后服务端返回项目配置版本，Web、EXE、APK 刷新导航和可执行动作。

### 8 3 组件依赖保持简单

单次打包上传依赖打包与上传能力。GM 启用时，界面直接展示所需能力并一并设置；停用依赖时，提示同时停用依赖它的入口。只维护这类少量明确依赖，不建立通用脚本编排和复杂依赖求解框架。

增量上传可以独立使用已有产物，不强制开启打包。Relay AI 制作可以独立使用，不强制开启 Jenkins。第三方订单同步失败不能阻断基础 Bug 操作。每个组件都应明确它需要的外部连接，缺少配置时显示“待配置”，不要让基础页面报错。

### 8 4 开关同时作用于执行

组件启用控制导航、页面、HTTP API、MCP、后台轮询、自动触发和新任务创建。前端隐藏按钮只是其中一部分。服务端在创建或执行新任务时检查项目开关，组件不能从定时任务或旧链接绕过配置。

停用组件时，停止接收新任务和新的自动触发。已排队但未开始的任务标记为暂停并保留记录；已运行任务默认允许安全完成，GM 可通过原有明确取消操作处理。已启动的单次打包上传按既定任务配置完成其已登记流程，界面应展示这些仍在运行的任务。不得直接杀进程或删除工作目录。

历史任务、日志、Bug 附件和已发布产物保持可查看。重新启用后先展示暂停任务，由员工明确恢复，不自动把停用期间的旧任务全部重新执行。修改连接配置时，新任务使用新版本，运行中的任务保留原执行配置与可用凭据引用。

### 8 5 不同项目的外部配置

Jenkins Job、分支、参数预设、ZIP 来源、上传渠道、Relay 外部项目均按项目绑定，移除当前代码中的固定项目预设。两个项目可以主动共用一套外部服务，但它们的任务和发布目标仍各自记录，GM 保存时应显示目标供核对。

现有打包链路中不支持的自动构建类型不能因组件化而假定已经支持，例如当前 iOS 自动构建限制仍需按真实能力显示。APK 和 EXE 的一致性是对同一项目暴露同样的业务能力与限制，不能一端假成功、另一端报不支持。

## 9 APK 与 EXE 同步兼容

### 9 1 同步交付的含义

项目制和组件化是一项同时覆盖 Android 与 Windows 的产品改造。两端均完成项目登录、所属项目切换、人员管理、基础 Bug 全流程、组件菜单和错误提示，使用同一套 API 合同。Web 同步更新其共享页面及兼容入口。

APK 不需要在手机里运行 Jenkins、上传器或 Relay 执行器。构建、服务器产物上传与 AI 制作都由服务端完成，APK 提交任务并查看进度、结果、日志和允许的任务动作。需要本地文件的入口使用 Android 文件选择与上传流程；服务器目录配置由 GM 或服务端维护。

### 9 2 必须覆盖的端侧改动

| 功能 | Windows EXE | Android APK |
| --- | --- | --- |
| 登录 | 项目入口与姓名登录，保留旧项目使用习惯 | 项目链接或二维码进入，姓名登录，保存已选项目 |
| 项目切换 | 所属项目列表，切换后刷新共享 Web 页面 | 原生列表和仓库上下文同步切换 |
| 人员管理 | 当前项目名单、关联、停用等现有操作 | 提供相同项目内操作和反馈 |
| Bug 流程 | 创建、编辑、附件、评论、完成、验收等 | 同等业务流程，保留移动端取证与文件处理 |
| 组件入口 | 服务端配置决定菜单、工具与动作 | 同一配置决定可见入口和支持动作 |
| 后台任务 | 项目明确的进度、通知、日志与结果 | 可提交和查看服务端任务，支持相同允许动作 |
| 本地保存 | 草稿、缓存、最近使用按服务地址与项目区分 | 本地仓库、偏好、未上传附件同样区分 |
| 更新迁移 | 旧配置自动绑定原项目，保留未提交内容 | 升级迁移原项目会话、草稿和文件，不清应用数据 |

### 9 3 请求和本地数据处理

EXE 与 Web 当前某些上传草稿只按用户保存，需要补充项目和服务地址。Android 已有包含项目的仓库上下文，但最近修复人等偏好仍需逐项检查，不能因为有一个 projectId 字段就认为全端已完成多项目兼容。

退出登录、切换项目、项目停用和员工被移除时，保留未同步的个人草稿和证据，阻止其误提交到另一个项目。重新进入原项目后可继续处理；如果已经失去该项目资格，允许用户看到本地未提交内容的存在并保存自己的文件，但不继续读取服务器中的其他项目内容。

不同窗口或不同客户端可同时打开不同项目。请求携带明确项目，不依赖服务端一个全局“当前项目”变量。通知点击后先核对项目再打开详情，避免用短编号跳到当前项目的另一个 Bug。

### 9 4 兼容和发布要求

第一阶段服务端保留旧项目和旧接口兼容，旧客户端明确绑定原项目；不能把它们自动接到新建的其他项目。多项目入口只对已支持该能力的客户端启用，需要升级时给出清楚提示。

正式验收必须同时产出可安装的 APK 与 EXE，验证项目选择、旧格式数据迁移、草稿保留、基础流程和组件开关。新版使用独立应用身份并能与日常版本共存；旧版升级兼容在专用测试配置、设备或模拟器中演练，不能覆盖用户正在使用的 EXE 或 APK。不要求 Android 与 Windows 使用相同安装版本号格式，但必须标明兼容的 API 合同和功能批次。只构建成功或只跑 Web 测试不足以通过。

## 10 历史数据迁移与上线步骤

### 10 1 保持原项目连续使用

1. 只读盘点当前生产项目 ID、人员 ID、Bug、修复历史、附件索引、上传队列、Relay 映射和组件配置，记录来源时点。
2. 使用一致性备份机制取得离线副本，保存到新版独立目录；不得直接复制正在变化的 SQLite 主文件而漏掉 WAL 中的数据。
3. 仅对离线副本或新版测试库做增量迁移，沿用原项目 ID，不重编号历史 Bug；生产原库保持原结构并继续工作。
4. 在新版登记原项目配置副本，外部执行连接默认停用或绑定独立测试目标；复制来的未完成任务必须暂停，不能重放生产队列。
5. 新建项目默认只有 Bug 管理；GM 明确开启额外组件并填写该项目连接。
6. 原有姓名人员继续映射到现有 ID，新登录增加项目归属；旧客户端保持绑定原项目。
7. APK 与 EXE 在专用测试环境完成升级迁移和共同验收，再在独立新版实例中开放第二个试用项目；本次不切换旧生产入口。

### 10 2 无项目字段的历史任务

原有上传记录或任务文件只有在来源明确属于现有项目时，才补记为原项目。存在多个来源且无法判断的记录保留为待确认，不按文件夹名、最后登录用户或最近项目进行猜测。

迁移前后核对各项目 Bug 数量、状态分布、评论数、附件索引、人员关系与未完成任务数量。核对数据的主要目的是确保原项目不丢记录、新项目不继承不属于自己的记录。不要为了完成迁移清空队列、附件、本地应用数据或工作目录。

### 10 3 回退和备份边界

数据库迁移优先新增字段、表和兼容读取，迁移与回退均先在新版测试数据副本中演练。旧生产继续连接自己的原库，不能让旧服务读取已迁移的新版库。新版出现问题时停止或回退新版实例即可，保留其新增操作和产物，不对生产数据库执行恢复或覆盖。

采用单数据库后，现有完整备份和恢复对应整个部署。不能承诺用全库备份只恢复一个项目而完全不影响其他项目。按项目逻辑导出与恢复可作为后续运维能力，首期先保证完整备份、迁移校验和可执行回退步骤。

## 11 开发工作拆解

### 11 1 业务与服务端

首先调整项目目录、姓名登录和成员管理，把固定项目值改为每次请求的明确项目。保留现有账号兼容字段、人员 ID 和基础状态机，再逐项改造列表、详情、附件、评论、事件、统计与状态动作。补齐 GM 项目管理及组件配置接口。

随后把 Bug 业务动作整理为 HTTP 和 MCP 共用服务。现有 HTTP 路由适配到共用服务，新增缺失 MCP 工具及服务端 MCP 入口，保留 EXE 本地兼容工具。同步编写可直接调用的 API 示例与 MCP 示例，并自动检查两者的动作覆盖范围。

### 11 2 组件拆分

从基础启动和导航中抽出 Jenkins、单次打包上传、增量上传、Relay 制作与第三方同步的注册。每个组件提供明确的配置、页面、API、MCP 和后台任务入口。第一期在同一代码仓库内实现即可。

上传独立队列和 Relay 状态文件应与业务组件拆分同批修改，避免组件代码已拆开但任务仍混在全局快照中。新增项目不得继承原项目凭据、发布路径或外部任务映射。

### 11 3 端侧与交付

Web 和 EXE 增加项目上下文及统一配置读取，处理异步刷新与草稿保存。Android 同时增加登录入口、项目切换、组件任务页面和本地迁移。两端使用同一组测试项目进行回归，避免开发阶段就把 APK 留到最后补做。

交付物包括数据库迁移脚本、项目与 GM 管理入口、组件配置、完整 HTTP 接口文档、MCP 工具目录、APK、EXE、迁移回退说明及验收记录。新功能代码通过后，还要证明安装后的客户端与实际 API 配合可用。

## 16 新工作树与生产并行运行

### 16 1 本次实施边界

使用新的 Git 工作树和独立开发分支制作全部程序改动，分支采用 codex 前缀。现有 `D:\Relay-QA-Hub` 主分支工作目录继续承担当前工作，不在其中修改应用代码、构建输出、生产脚本或运行配置。本次对设计文档的更新属于方案交付，后续开发把这份文档复制到新工作树并记录版本与来源。

先核对工作树路径、分支、起始提交、未提交改动及生产进程的实际启动路径，再安装依赖和运行任何脚本。Git 工作树会共享仓库对象和引用，它不会自动分开数据库、环境变量、全局工具配置、绝对路径和外部服务。开发脚本中指向原目录的路径必须检查，不能以“已经是新工作树”为理由默认安全。

本次授权包含在独立环境完成实现、构建、运行和真实测试。它不包含合并 main、推送到生产分支、覆盖生产发布文件、重启生产服务、关闭日常 EXE、卸载或覆盖日常 APK。既往“验证后直接发布”的习惯在本任务中只适用于独立预览通道，不能解释为生产替换授权。

### 16 2 必须独立的运行资源

| 资源 | 新版要求 | 旧生产保护要求 |
| --- | --- | --- |
| 代码与产物 | 新工作树、独立分支、独立输出目录 | 不在原目录执行清理、重置、重编译或覆盖 |
| API Web MCP | 独立实例及实测空闲端口，记录监听地址和进程 | 不占用现有端口，不替换反向代理与生产路由 |
| 数据库 | 独立 SQLite 文件及 WAL、SHM、备份目录 | 不引用生产库路径，不执行生产迁移 |
| 附件与缓存 | 新根目录，导入副本具有独立可写路径 | 不使用指向生产可写目录的链接或 junction |
| 队列与外部状态 | 独立上传库、outbox、Relay 映射和任务日志 | 导入任务默认暂停，不重放旧生产任务 |
| 配置与凭据 | 独立配置文件、凭据命名和明确测试连接 | 不改系统级默认值，不覆盖生产凭据项 |
| 进程与后台服务 | 独立实例 ID、日志、PID、服务与计划任务名 | 停止脚本只管理新版进程，不按通用进程名杀进程 |
| EXE | 独立应用标识、用户目录、单实例锁、快捷方式与协议 | 日常 EXE 同时运行，配置、会话和更新源保持原样 |
| APK | 独立 applicationId 与 provider 等派生标识，名称清楚区分 | 同设备可共存，不卸载、不覆盖、不清日常应用数据 |
| Web 登录 | 独立浏览器存储及会话 cookie 名称或独立主机名 | 不能仅凭端口不同就假定 cookie 已隔离 |
| 发布与升级 | 独立下载目录、更新清单、版本通道和目标检查 | 不覆盖生产安装包、下载地址、更新 manifest |
| 外部执行 | 独立 Job、工作区、测试项目、上传前缀或频道 | 不发布到生产 CDN 路径，不改真实订单和当前制作任务 |

Windows 还需核对应用用户模型 ID、通知跳转、自动更新安装位置和凭据存储键。Android 还需核对深链、文件提供者 authorities、后台任务和通知归属。两端打开通知、更新或附件时，不能启动旧版或回连生产 API。

浏览器 cookie 不按端口区分，Web 页面即使换了端口也可能干扰旧登录。因此新版必须使用独立 cookie 名称或独立主机名；跨域、WebSocket、下载、MCP 和 CSRF 配置都明确指向新版服务。

### 16 3 启动与停止必须可核对

提供新版专用启动、停止、状态查看和日志入口，普通维护人员可以照说明手动操作。启动脚本输出实例名称、工作树、API/Web/MCP 地址及数据根目录，不输出凭据。没有明确填写新版配置时直接停止并提示，不能回退到生产默认配置。

启动前解析真实绝对路径并检查数据库、附件、队列、备份、发布目录不落在已识别生产目录内；同时核对端口和服务名没有冲突。检查目录链接的最终指向。运行时继续保留实例标识，帮助日志和测试结果辨认环境。

停止脚本只作用于本次实例创建并核对过的 PID、进程启动时间、命令行路径或独立服务名。新版启动失败、端口冲突、迁移失败时不得通过杀掉旧进程、改生产端口、借用生产目录或重启宿主机解决。

### 16 4 数据副本与外部服务

初始演练优先使用独立测试数据；需要验证历史兼容时，从生产取得一致性备份并在新版目录中恢复。数据副本要记录来源时间，但不建立新旧双向写入或自动同步。新版测试产生的 Bug、评论、状态与附件不回写生产。

从生产复制的定时任务、上传命令、outbox 和外部连接默认禁止执行，待绑定独立测试目标后才启用。真实 Jenkins、上传器或 Relay 可以是现有平台上的专用测试 Job、项目和发布目录，但必须确保输入、工作区、输出、回调和任务关联都属于测试环境。

先检查磁盘、CPU、内存及 Worker 是否有可用容量，再开展真实构建。使用保守并发上限，不抢占生产任务、不清理生产缓存。若共享硬件无法提供不影响日常工作的测试容量，继续其他功能制作并登记具体待验证项，待独立资源可用再执行；不能为了赶进度影响生产。

### 16 5 并行运行的验收

记录旧生产的分支与提交、运行路径、监听地址、配置及更新文件校验值和就绪状态。测试开始、关键任务前后、新版停止后分别只读核对旧生产可用性。生产人员正常操作会让业务数据变化，不以生产数据库哈希不变作为判定条件，而是检查新版没有连接或写入生产资源。

至少完成新旧 EXE 同开、新旧 APK 共存、新旧 Web 登录互不覆盖、API 与 MCP 并行、独立更新演练以及新版异常退出后的旧版可用性检查。故障演练只针对新版进程和测试目录；不对生产注入错误，也不通过真实生产 Bug 写操作证明旧版健康。

制作完成后保留独立运行入口、安装包、数据目录、日志和停止说明。新版故障的处置是停止或回退新版；现有工作继续使用旧入口。任何未来生产切换都需要单独安排数据合并、切换窗口和回退步骤，不属于本次完成条件。
