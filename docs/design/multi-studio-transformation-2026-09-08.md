本文评估在现有本机部署上，为其他工作室提供 QA Hub 服务所需的改造。范围包括工作室选择、数据隔离、成员与权限、可选功能组件、打包与上传适配、运行资源、历史数据迁移和上线验收。

结论是可以沿用当前项目，但应按一次产品架构改造安排。现有数据库已经具备账号与项目归属字段；真正的缺口集中在单账号运行假设、姓名登录、全局打包服务、共享上传记录、固定外部配置以及跨工作室的运行和恢复边界。

建议采用统一入口和同一套客户端，在本机为各工作室配置独立 API 实例、数据库、文件目录与集成凭据；功能通过统一的模块目录配置。现有工作室保持原 ID 和数据目录，新增工作室从空白业务库开通。构建执行器按工作室隔离；需要共享的硬件采用配额和公平排队。单台物理机仍存在共同故障风险，不能承诺断电、硬盘故障和宿主机宕机时互不影响。

## 1 调研依据与适用范围

本方案依据本地源码静态检查编写。检查时 Git HEAD 为 `62b4495c9b28dc3aea1d5633e870be4e1fdf841f`，桌面包声明版本为 `3.3.5`，初始工作区无未提交修改。本文没有通过创建工作室、执行打包、操作生产数据库或重启服务来验证未来方案。源码版本不等于本机已安装或线上正在运行的版本。

重点检查了 API 的启动装配与认证、SQLite 模型和存储适配器、上传队列与打包服务、Web 导航与草稿、桌面通知与 MCP、Android 本地作用域，以及备份恢复相关代码。具体证据见第 17 节。README 存在早期流程和版本说明，冲突时以当前源码与已接受的架构决策为依据。

以下规模仅用于方案和工作量估算：首批 2 至 5 个工作室，每个工作室约 10 至 30 名使用者，首期兼容已有 Jenkins 与上传器。没有进行容量压测，也没有调查其他工作室的实际流水线。新增不同引擎、不同上传平台或大规模并发，需另行评估。

本文中的接口、表名、目录结构、配额和时间安排均为建议设计，不表示已经实现。业务模块开关不能替代用户权限，工作室名称也不能作为安全身份。

## 2 当前项目能复用什么

### 2 1 已有基础与主要缺口

| 领域 | 已有基础 | 需要改造的部分 |
| --- | --- | --- |
| 数据归属 | `accounts`、`projects`、`users`，主要业务表带 `account_id` 和 `project_id`，已有复合外键 | 让工作室成为真实可配置运行边界，核查所有业务与旁路存储 |
| Bug 流程 | 修复轮次、人工完成、验收、版本控制、幂等与审计 | 保留流程语义，补齐跨工作室拒绝测试 |
| 项目权限 | 项目成员和角色模型已经存在 | 增加平台与工作室管理权限，审查各路由实际权限执行 |
| 登录 | 浏览器会话、令牌摘要、CSRF、凭据存储基础 | 当前公开登录只收姓名，需改为可验证身份与邀请加入 |
| 上传 | 服务端持久队列、任务恢复、按上传人保存凭据 | 队列、快照、日志、锁、产物和凭据需要工作室边界 |
| 打包 | Jenkins 触发、队列与进度展示、打包后衔接上传 | 固定任务、地址与预设抽为工作室和项目级适配配置 |
| 客户端 | 共用 Web，Windows 壳，Android 本地作用域基础 | 工作室切换、旧请求作废、缓存命名空间、会话与草稿保留 |
| 备份 | 主业务库在线备份、附件清单、恢复与异盘归档 | 每工作室独立恢复，并纳入队列、集成状态和配置依赖 |

数据库中的 `modules` 是项目内的 Bug 业务分类，不是可安装的功能组件。新增功能模块目录必须使用其他命名，例如 `feature_catalog`，避免把两种概念混在一起。

### 2 2 目前单工作室假设的位置

`apps/api/src/main.ts` 的 `MOBILE_SCOPE` 固定了账号和项目，启动时多个 `createSqliteMobile…Store` 都接收同一份 scope；姓名目录和人员种子也围绕这个账号加载。`app.ts` 的认证桥接还会校验会话账号必须等于启动配置账号，再适配现有路由。

因此，直接在界面上增加工作室下拉框，而不改变启动配置和请求授权边界，不能让同一进程正确服务多个工作室。采用每工作室独立实例时，可以先把固定 scope 改为实例配置，复用大量现有存储实现；如果选择共享单进程，则需要把这些存储接口系统性改为请求级上下文。

### 2 3 上传链路是需要优先处理的共享点

`IncrementUploadService` 使用独立 `queue.sqlite`，主要记录 `owner`，没有工作室与项目字段。`snapshot()` 会读取所有上传人的任务，`buildChains()` 也汇总各上传人的打包链。这是当前团队共享记录的既有设计，扩展后应保持“同一工作室内按权限共享”，并切断跨工作室读取。

上传凭据目前按 `owners/<owner>/auth.json` 保存，`accountIdentity` 表示外部上传平台的账号指纹，不等于 QA Hub 的工作室账号。不能直接把这个字段当成工作室 ID。队列和任务文件需要独立的 `accountId`、`projectId`、`integrationId` 和 `ownerId`。

`jenkins-builds.ts` 绑定现有 OZDQP 的任务、下载路径与构建预设；`uploader-host.ts` 包含固定平台地址与默认 ZIP 来源。这些能力需要封装成当前项目适配器，不能成为所有新工作室的默认连接配置。

## 3 产品体验与边界

### 3 1 工作室与项目的关系

层级建议为：平台 → 工作室 → 项目 → Bug、制作任务、构建、上传、证据和通知。一个工作室可以拥有多个项目。工作室成员身份与项目成员身份分开管理；加入工作室不自动获得全部项目的访问权。

技术上优先将现有 `accounts` 解释为工作室，保持 `account_id` 的含义一致。前端可以显示“工作室”，无需把现有数据库列全部改名为 `studio_id`。控制目录中的工作室 ID 与业务库 `accounts.id` 一一对应，现有账号 ID 原样保留。

### 3 2 用户使用流程

1. 用户通过可验证身份登录。平台只返回该身份已加入且可使用的工作室，不向匿名用户公开完整工作室名录。
2. 只有一个工作室时自动进入；有多个时显示选择页。首次加入通过邀请链接完成，输入或猜到工作室名称不构成加入授权。
3. 顶部持续显示当前工作室、当前项目和当前用户。工作室切换与项目切换使用独立控件。
4. 进入工作室后加载它的功能配置，只展示已启用且用户可以使用的入口。
5. 提交打包、上传或发布时显示项目、目标平台、渠道和版本，结果页可以追溯到原始工作室与发起人。

切换工作室应先保存原工作室草稿，停止旧页面订阅并使未完成请求失效，再加载新作用域。已经提交的后台任务继续绑定原工作室运行，不能因页面切换迁移归属。未提交内容留在原工作室，恢复时仍需要原作用域授权。

### 3 3 管理界面

平台管理包含工作室开通、停用、资源额度、功能授权、实例状态和版本。工作室管理包含名称与标识、成员邀请、角色、项目、已授权模块的启停、集成配置和审计。平台管理员默认只管理控制信息；查看业务内容应使用显式、限时、可审计的支持授权。

初期采用功能模块和少量可配置表单，不为每个工作室维护独立代码分支或单独编译一套 EXE。图标、名称、预设与页面顺序可以作为配置；任意脚本、页面代码和自定义流程引擎放在后续阶段。

## 4 部署与数据隔离方案

### 4 1 三种方案比较

| 方案 | 数据边界与恢复 | 对现有代码的影响 | 适用判断 |
| --- | --- | --- | --- |
| 单进程单库按工作室过滤 | 隔离依赖每条查询；单工作室恢复较复杂 | scope 和所有旁路都要改为请求级；数据库迁移较少 | 可行，但不作为首批外部工作室推荐方案 |
| 同机统一入口 每工作室独立实例和数据库 | 业务库、文件、重启和恢复独立；硬件仍共享 | 增加控制目录与路由；固定 scope 配置化；大量存储可复用 | 本次推荐 |
| 每工作室独立虚拟机或独立主机 | 服务和执行环境隔离更强；独立主机可减少共同故障 | 运维和资源投入更多，仍需权限与模块设计 | 有源码执行或更高隔离要求的工作室 |

推荐方案不是复制多份长期分叉源码。所有工作室运行同一套经过验证的发布产物，实例只拥有不同配置和数据目录。控制面维护实例清单、部署版本和兼容状态；迁移逐实例执行，可以分批验证。

SQLite 每个数据库文件同一时刻仅允许一个写入者，适合保留现有本地 API 存储方式；拆分工作室数据库可以分开写锁和恢复范围。该判断来自 SQLite 官方说明，并不代表当前机器已通过目标容量验证。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

### 4 2 建议结构

```text
Web 和 Windows 和 Android
        ↓ HTTPS 统一入口
控制目录与身份服务
  工作室名录 成员映射 模块授权 实例路由
        ↓ 已验证的工作室上下文
 ┌ 工作室 A API ─ A 业务库 证据 队列 集成配置
 └ 工作室 B API ─ B 业务库 证据 队列 集成配置
        ↓ 已授权的执行任务
工作室专属执行器 或 受配额控制的共享执行资源
        ↓
各自 Jenkins Relay 上传平台和产物仓库
```

图中的控制目录只持有身份、配置与路由等控制信息，不汇总业务附件、源码或第三方密钥。业务 API 绑定一个工作室，启动时验证配置账号与数据库账号一致；收到其他工作室上下文必须拒绝，不能自动纠正为默认工作室。

第一阶段可保留当前工作室的兼容入口和原运行根目录；新统一入口按已验证身份和工作室路由到实例。下游端口限制为回环或受控内部网络。不能让外部用户绕过入口直接访问沿用调试令牌的旧 API。

### 4 3 本机目录建议

```text
D:\Relay-QA-Hub-Control\
  registry.sqlite
  deployments\

D:\Relay-QA-Hub-Data\production\
  现有工作室目录保持不变 通过注册项绑定

D:\Relay-QA-Hub-Data\studios\<accountId>\
  db\qa-hub.sqlite
  evidence\sha256\
  quarantine\
  integrations\increment-upload\queue.sqlite
  integrations\production\
  jobs\ artifacts\ logs\ config\

E:\Relay-QA-Hub-Archives\studios\<accountId>\
  <recoveryPointId>\
```

以上是建议路径，新路径必须先核对本机卷、容量、权限和备份策略。现有上传等目录可继续使用原结构，通过工作室根目录提供边界，不强制一次性搬迁。目录只能由服务端已注册 ID 解析，禁止客户端提交绝对路径、相对跳转或 junction 目标。

同一 Windows 账号下的不同目录不构成操作系统安全边界。建议业务服务使用最小权限服务账号和 NTFS ACL；构建外部工作室源码时使用专属 VM 或执行机，并隔离仓库凭据、工作区、缓存和发布权限。

### 4 4 单机能承诺的隔离范围

可以通过设计和验收提供业务记录隔离、权限隔离、外部账号隔离、独立恢复和有界资源使用。单机无法消除 CPU、磁盘、带宽和宿主机故障的共同影响。平台自身升级也可能影响全部实例，需要逐工作室发布和兼容版本控制。

如果要求某工作室执行任意项目脚本而无法接触其他工作室数据，应至少配置独立执行 VM。若要求一台物理机故障不影响其他工作室，则需要不同主机和独立故障域，超出“仅在当前机器改造”的边界。

## 5 身份验证与权限设计

### 5 1 登录必须升级

当前姓名登录可以复用或自动创建用户，显示名不是秘密，不能证明操作者身份。对外工作室需启用邀请制和密码、企业身份提供方或经验证的一次性登录方式。已有 `local_credentials` 和会话机制可复用，但需要补齐注册邀请、密码初始化、找回、撤销和服务端过期检查。

显示名只用于展示，不能用于合并两个工作室的用户。历史用户 ID、Bug 作者、修复人和验收人必须保留。新登录身份通过明确映射连接到原用户；映射由本人验证和管理员核对，不按中文姓名、拼音或邮箱相似度自动认领。

建议建立最小全局登录主体 `principals`，用稳定身份映射到各工作室的本地 `users.id`。它只解决“这个登录者在此工作室对应哪个人”，不把工作室用户表整体改造成全球共享人员表。第一阶段若暂不提供统一身份，可使用独立工作室登录，但切换其他工作室要独立验证，不承诺无感切换。

### 5 2 作用域与会话

服务端统一生成 `RequestContext`，包含 `principalId`、`accountId`、`actorId`、`projectId`、角色、`sessionId` 与 `policyRevision`。`projectId` 由路由请求选定，再验证属于该工作室且用户有成员资格。所有读取和操作都使用已验证上下文。

客户端选择的工作室只是请求参数。入口必须检查成员身份，剥离外部伪造的内部头，再签发短时、限定目标实例的内部身份断言；下游验证签名、受众、时效和工作室一致性。实例内的固定 account 配置可作为第二道拒绝边界。不得仅信任 `X-Studio-Id` 或旧调试 Bearer。

多浏览器标签页可能同时打开不同工作室，不能用“会话里一个可变 currentStudio”决定所有写入。每个页面和后台作业都绑定明确工作室；切换时只改变当前页面上下文。会话撤销、成员退出和工作室停用必须有明确生效上限，建议请求即时校验，缓存最长 60 秒；发布操作执行前再次校验。

### 5 3 角色与兼容策略

| 角色 | 建议权限 | 不默认包含 |
| --- | --- | --- |
| 平台管理员 | 开通工作室、分配模块与资源、部署和恢复编排 | 所有工作室的业务阅读、第三方平台发布 |
| 工作室管理员 | 管理本工作室成员、项目和已授权模块配置 | 其他工作室信息、任意主机操作 |
| 项目管理员 | 管理项目成员和配置 | 工作室开通、平台凭据 |
| 项目成员 | 按工作室策略进行 Bug 协作和人工处理 | 任意打包发布和人员授权 |
| 发布负责人 | 指定项目与渠道的构建、上传、最终发布 | 其他项目渠道、密钥明文读取 |
| 服务身份 | 指定工作室、项目与操作范围的自动化 | 人工验收、平台管理权限 |

现有工作室的项目成员协作规则应保持，包括人工标记完成、验收和已有共享管理行为。新增管理与发布权限必须显式迁移并回读，不能在改造中无意收紧现有流程。对新工作室可采用更细角色，但应由已配置策略决定。

启用 Relay、打包或上传，均不改变 QA Hub 是 Bug 生命周期事实源的原则。人工完成不能等待自动执行器；第三方同步失败应记录并可重试，不能阻止本地人工处理。禁用可选模块也不能让已提交 Bug 无法验收。

## 6 功能组件化设计

### 6 1 组件粒度

建议先定义固定、经过发布验证的能力目录，再按工作室启用。首期使用代码内注册的组件与服务端配置，不引入任意第三方插件执行机制。可选组件的配置由服务器持久化，前端菜单、API、后台任务和桌面 MCP 都读取同一个授权结果。

用户提出的“打包上传、单次打包上传、增量上传”在当前代码里存在重叠。本文暂把“单次”定义为人工发起一次流水线，把“自动”定义为由定时或任务完成触发。二者复用执行步骤，但使用不同权限和触发配置。开工时应通过一个实际案例确认产品命名，无需为每个按钮复制执行逻辑。

| 能力键 建议 | 产品入口或用途 | 依赖与边界 |
| --- | --- | --- |
| `qa.core` | Bug 上报、详情、人工完成、验收、证据 | 工作室基本能力，单独停用工作室才冻结访问 |
| `production.tasks` | 制作任务与任务管理 | 项目成员权限；自动执行另依赖 Relay |
| `integration.relay` | AI 修复与 Relay 执行 | 配置工作室专属连接与项目映射 |
| `integration.qingyu` | 轻语导入和同步 | 配置所属平台与个人或工作室凭据 |
| `build.single` | 单次打包 | 构建适配器、项目和执行配额 |
| `package.download` | 查看和下载本项目产物 | 产物授权，与是否允许发起构建分开 |
| `upload.existing` | 上传已有包 | 上传适配器和经过授权的来源 |
| `upload.incremental` | 上传已有增量包 | 增量格式兼容校验，不等于进行增量构建 |
| `build_upload.single` | 单次打包后上传 | `build.single` 和对应上传能力；绑定本次产物 |
| `build_upload.automatic` | 定时或事件驱动打包上传 | 单次流水线能力、触发规则、去重与配额 |
| `build.incremental` | 真正的增量构建 | 执行器支持、可信基线与兼容性证据 |

Android、Windows、iOS 是构建或上传适配器声明的支持平台，不应把每一种平台都做成全局硬编码分支。当前自动打包上传路径存在 Android 约束，已有 iOS ZIP 上传应作为独立能力保留，不能因显示 iOS 选项就表示具备 iOS 构建机。

### 6 2 三种工作室配置示例

| 能力 | A 现有完整协作 | B 只做 QA | C QA 与手动发布 |
| --- | --- | --- | --- |
| Bug 与人工验收 | 开 | 开 | 开 |
| 制作任务和 Relay | 按现有配置 | 关 | 关 |
| 单次打包 | 开 | 关 | 开 |
| 已有包或增量包上传 | 开 | 关 | 开 |
| 单次打包后上传 | 开 | 关 | 开 |
| 自动触发打包上传 | 另行配置 | 关 | 关 |
| 轻语 | 按现有配置 | 按需 | 按需 |

A 的“开”表示迁移目标，需要从真实运行配置确认。源码中存在页面不证明该工作室已完成该能力的生产开通。新工作室默认只启用基础能力，不能自动继承 A 的平台账号、产品 ID、仓库和渠道。

### 6 3 配置结构与生效规则

建议 `feature_catalog` 记录能力键、版本、依赖、支持平台、客户端最低版本和配置 schema；`studio_features` 记录工作室授权、管理员启停、配置、修订号与变更人；`project_feature_overrides` 只允许项目在工作室授权范围内进一步收紧。

有效能力等于平台授权、工作室启用、项目允许、用户权限和运行条件同时满足。前端隐藏入口只是显示结果，后台必须再次执行相同校验。配置缺失、未知功能键或无法验证的旧配置默认拒绝新操作，并返回可理解的原因。

建议配置示例：

```json
{
  "accountId": "<工作室UUID>",
  "revision": 8,
  "features": {
    "qa.core": { "enabled": true },
    "build.single": { "enabled": true },
    "upload.incremental": { "enabled": true },
    "build_upload.single": { "enabled": true },
    "build_upload.automatic": { "enabled": false }
  },
  "limits": { "activeBuilds": 1, "activeUploads": 1 },
  "integrations": ["<集成配置ID>"]
}
```

运行中关闭模块，应停止接收新作业；已排队作业在派发前重查配置并进入“配置已停用”的暂停状态。已经执行的构建允许安全结束并保存产物，最终对外发布必须重查发布权限和模块状态；正在进行的不可逆发布记录真实结果，不伪造取消成功。历史记录仍按基础访问权限可读。

每次修改保存 `expectedVersion`、幂等键、修改前后差异和审计。配置更新推送修订号，客户端和服务端缓存失效；前端直接访问旧路由、MCP 或重放任务都不能绕过开关。先保存配置草稿，校验依赖与连接，再原子启用新修订。

## 7 数据模型与存储改造

### 7 1 控制目录和业务库职责

| 数据位置 | 建议数据对象 | 设计要求 |
| --- | --- | --- |
| 控制目录 | `studios`、`studio_instances` | ID、状态、实例地址、部署和 schema 版本；路径只允许管理员配置 |
| 控制目录 | `principals`、`studio_memberships` | 可验证身份与工作室成员关系；保留本地用户映射 |
| 控制目录 | `studio_features`、`feature_catalog` | 功能授权、配置版本和支持条件 |
| 业务库 | 现有 `accounts`、`users`、`projects` 与 Bug 表 | 保留 ID、外键、版本和审计；业务仍归本工作室 |
| 业务库 | `integration_configs`、`project_integrations` | 类型、项目、非敏感参数与 `secretRef`；不保存可返回的密钥明文 |
| 队列与任务存储 | 上传命令、流水线、执行回执 | 显式工作室、项目、连接、渠道、操作者和配置修订 |
| 文件与产物目录 | 附件、隔离区、构建包、日志、收据 | 根目录独立；所有读取先验证对象归属 |

跨控制目录和业务库的开通无法依靠一个普通 SQLite 事务原子完成。应使用可恢复的开通流程：预留工作室 ID → 创建目录与空库 → 创建本地管理员映射 → 验证健康 → 发布路由。阶段记录幂等回执，失败保持 `provisioning_failed`，业务入口只接纳全部完成的 `active` 实例。

### 7 2 需要保留或新增的约束

同名项目和同名人员允许出现在不同工作室。业务外键继续携带 `account_id`；Bug 编号继续按工作室和项目边界生成，不能因界面文案改名重排历史编号。以 `LOCAL-123` 这类短编号读取时，必须同时提供已授权工作室与项目。

新增幂等键至少限定 `accountId + projectId + actorId + operation + clientRequestId`，并保存请求摘要。对同一键的不同请求返回冲突，不能覆盖旧结果。外部任务号、构建号和渠道号的唯一性必须包含对应 `integrationId`，不能假设所有 Jenkins 都只有一个编号空间。

即使使用独立数据库，队列和收据也要写工作室 ID，方便恢复、导出和回调核对。迁移旧队列时由注册项明确赋予现有工作室归属；无法证明项目归属的旧任务保持只读并人工确认，不能默认归到第一个项目。

### 7 3 附件与下载

当前附件文件以 SHA-256 地址存放，数据库记录已有账号与项目约束。新方案继续使用哈希校验，但每工作室独立根目录；首期不做跨工作室物理去重，以降低删除、恢复和存在性泄露的复杂度。

附件下载、缩略图、Poco 数据、日志、二维码、构建包和 MCP materialize 都要从已授权对象获得文件地址。不要通过公开静态目录或可猜测的“最新包”路径绕过业务授权。需要分享时生成限定对象、短时有效、可撤销的下载授权；响应、代理与 CDN 缓存必须避免跨工作室复用。

## 8 打包上传与执行器改造

### 8 1 适配器边界

建议定义 `BuildProvider`、`UploadProvider` 和 `ArtifactStore`。构建接口覆盖预检、提交、查询、取消、获取产物清单；上传接口覆盖目标验证、提交、状态、恢复、测试结论与最终发布；产物接口提供按工作室授权的稳定产物定位与校验。

现有 Jenkins 和 OZDQP 上传器作为首个适配实现。`productId`、`channelId`、构建预设、下载地址、支持平台与身份来源由配置决定。普通用户只从服务器允许的项目和目标中选择；不能提交任意 Jenkins URL、脚本、服务器路径或外部下载地址。

新增上传目标要验证服务器网络访问范围、TLS、凭据权限、产物格式和回执能力。工作室管理员配置外部连接不等于获得访问本机内部任意地址的权限；连接测试使用受控地址范围，避免通过适配器访问其他工作室服务。

凭据需要区分工作室共享连接与个人外部登录。现有凭据文件与源码中的认证配置应做一次清单检查，迁移为受 ACL 保护的密钥引用或加密文件；对外响应只返回是否已配置、权限范围和轮换时间。密钥轮换保留操作审计，备份需要配套密钥恢复演练，不能只备份无法解密的密文。

### 8 2 每次任务绑定的事实

每个作业创建时固化 `accountId`、`projectId`、`actorId`、`integrationId`、源代码提交、平台、渠道、构建参数、模块修订、执行器要求和幂等 ID。后台从作业事实恢复上下文，不读取页面当前工作室或一个全局“当前账号”。

打包后上传必须绑定本次构建的不可变产物。建议使用 `buildId`、源提交、工具链指纹、产物 SHA-256 与 Manifest 摘要，保存到流水线回执。现有对共享 ZIP 的更新时间和头信息核验可以作为兼容保护，但跨工作室后应逐步改为每次构建唯一产物地址。

上传任务在进入最终发布前再次核对外部身份与目标。凭据轮换导致账号变化时暂停并显示原因，不能换成工作室当前默认账号继续。重试从原回执恢复，不能悄悄下载“最新包”并发布成原版本。

### 8 3 队列与互不干扰

工作室分别拥有业务队列，调度层限制各工作室的并发数、排队数、存储与带宽；对共享执行资源采用轮转或加权公平调度，避免一个工作室持续占满全部执行槽。界面只展示本工作室队列和等待原因，不显示其他工作室的项目名称。

资源互斥键要区分逻辑任务隔离与真实发布冲突。工作室独立平台账号时，可使用 `accountId + integrationId + projectId + target`；若两个连接实际写入同一外部账号、产品和渠道，即使来自不同工作室，也必须通过全局规范化目标锁防止覆盖，并明确管理授权。简单给原锁前面加工作室 ID 可能放开真实冲突。

当前共享 Jenkins 或全局 ZIP 来源在未完成改造前仍需串行保护。只有工作区、产物路径、外部目标和执行器都已分离，才可以增加并发。任务离开页面后继续执行，但取消、重试和恢复必须验证它原有的归属。

### 8 4 增量构建的特殊要求

“上传已有增量 ZIP”只负责传输与发布；“增量构建”还要保证生成内容正确。若将来提供 Unity 增量构建模块，应由构建适配器声明支持情况，并验证源提交、构建工具版本、基础 Player、Manifest 与依赖闭包。缺乏可信基线时明确回退完整构建，不能仅按文件夹裁剪资源。

不能因上传功能可用就宣称 Unity 增量构建可用或达到固定耗时。本次未验证其他仓库的最新构建状态；该能力必须单独完成真实构建、产物校验和运行加载验收后才能对工作室开放。

### 8 5 外部故障和人工接管

Relay、Jenkins、上传平台或轻语超时，不应占用主业务数据库事务。使用持久 outbox、可恢复回执、超时和重试，回调通过工作室专属密钥校验来源与任务关联。重复、延迟、乱序和工作室停用后的回调必须有确定处理规则。

外部完成只能更新其对应任务事实。Relay 完成不能自动关闭 QA Bug；人工接管后的旧回调不得覆盖新人工修复轮次。人工关闭本地问题时，外部同步失败作为独立状态保留和重试。

## 9 各端代码改造清单

### 9 1 API 与存储

`main.ts` 将 `MOBILE_SCOPE`、人员种子、集成连接、目录和服务参数变为实例配置，新增配置校验与工作室一致性检查。`app.ts` 逐步替换“认证后转换为统一调试令牌”的路由桥接，改为显式上下文和权限校验，并接入统一功能检查。

`sqlite-mobile-*.ts` 保留已有存储实现，明确实例绑定账号与路由项目选择的区别；涉及多个项目的创建、附件、验收与通知路径逐项校验，不能只修改列表查询。`packages/domain` 保持业务状态机，只补充工作室上下文与策略入口。

`increment-upload.ts` 补齐队列 schema 迁移、作用域读取、审计和配额；`jenkins-builds.ts` 与 `uploader-host.ts` 配置化并实现适配器。`production-tasks.ts` 的批次文件、附件文件、连接配置与回调身份都需要纳入工作室注册和恢复清单。

### 9 2 Web

`AuthGate.tsx` 接入正式登录与邀请；`App.tsx` 增加工作室选择及作用域容器，菜单依据服务端能力生成。新增工作室管理、功能管理与连接配置页面。`PackagingPage.tsx`、`UploadIncrementPage.tsx`、`BuildUploadControls.tsx` 接收项目与能力上下文，取消固定目标假设。

Web 的草稿、筛选、当前页、任务监控和缓存 key 建议包含 `serverOrigin + accountId + projectId + actorId`。当前上传草稿按 `userId` 保存，需要增加作用域。切换时使用请求代次或取消信号，使旧响应无法覆盖新工作室页面；已选择的修复人与验收人草稿也必须继续遵守已有防刷新覆盖规则。

### 9 3 Windows 与 MCP

统一 EXE 保持共用页面，新增工作室会话与服务入口兼容信息。通知订阅和历史按服务器、工作室和用户隔离；通知点击进入原工作室时先验证权限。托盘、下载队列、外部链接、IPC 和本地 MCP 不能只依赖最后打开的页面。

MCP 提供列出已授权工作室和读取当前上下文的能力。查询与修改命令显式绑定工作室和项目，写操作返回所属工作室与审计回执。多个工作室存在同一短 Bug 编号时拒绝模糊匹配。禁用模块后，对应工具返回明确不可用原因，不能继续走隐藏的原入口。

客户端更新应保留原服务器配置、已验证会话、草稿和回退目录，处理新旧服务器的能力协商。普通 QA 客户端更新包可统一分发；客户项目构建包必须按工作室授权，二者不要共用无鉴权下载目录。

### 9 4 Android

`ScopedRepository.kt` 已有账号、项目、操作者、安装和会话作用域，可以复用。需要检查登录选择、`QaRuntimeConfig`、`MainActivity`、草稿偏好、采集草稿与离线队列的入口是否全部遵守此边界，并增加服务器实例 ID，避免连接不同服务时本地 ID 冲突。

离线草稿和附件操作保持原始工作室归属。切换工作室或原权限撤销时暂停上传，不能把旧草稿自动提交到新工作室。切换不是清空数据；默认保留未同步内容并提供明确恢复入口。旧 APK 无法识别多工作室授权时限制在原工作室，不能默认为新工作室。

### 9 5 契约与脚本

`packages/contracts`、`packages/upload-contract`、Web API 类型、桌面桥接类型与 Android 网络模型同步新增上下文、模块配置和兼容错误。新增工作室开通、暂停、状态检查、备份和恢复脚本，所有脚本以注册工作室 ID 解析路径并输出审计结果。

建议增加 `studio-context`、`feature-registry`、`integration-adapters` 等共享包，具体拆包以依赖边界为准。首次不拆成大量微服务，也不同时全面更换数据库、前端框架和执行器。

## 10 建议接口与错误语义

接口仅示意，正式实现应更新 OpenAPI 与兼容测试。统一入口可以采用工作室前缀，实例内部继续使用原 `/api/v1` 路由；所有写操作服务端验证上下文，不把路径 ID 当授权。

| 方法与入口 | 用途 | 主要检查 |
| --- | --- | --- |
| `GET /api/v1/me/studios` | 列出已加入工作室 | 已验证登录主体，过滤停用与撤销关系 |
| `POST /api/v1/admin/studios` | 开通工作室 | 平台管理权、幂等回执、配置校验 |
| `GET /s/{accountId}/api/v1/context` | 返回成员、项目和有效模块 | 身份映射、工作室状态、实例匹配 |
| `PATCH /api/v1/admin/studios/{id}/features` | 保存模块配置 | 管理权、依赖检查、`expectedVersion` |
| `POST /s/{id}/api/v1/projects/{projectId}/builds` | 创建单次构建 | 项目归属、能力、构建权、配额 |
| `POST /s/{id}/api/v1/projects/{projectId}/pipelines` | 打包后上传 | 流水线权限、源提交、目标与配置快照 |
| `GET /s/{id}/api/v1/artifacts/{artifactId}` | 下载构建产物 | 工作室及项目归属、下载权限 |

未登录返回 401；缺少权限或能力返回 403；跨工作室对象可统一返回 404，避免暴露存在性；配置版本冲突返回 409；请求配额返回 429 并给出重试信息；依赖不可用返回 503。具体业务状态使用稳定错误码，例如 `FEATURE_DISABLED`、`STUDIO_SUSPENDED`、`INTEGRATION_NOT_CONFIGURED`。

后台恢复和回调也使用同一套作用域检查。对外响应不返回密钥、内部绝对路径、其他工作室标识或原始上游认证错误内容。

## 11 迁移与上线步骤

### 11 1 准备与演练

1. 盘点真实数据根、当前账号和项目 ID、全部用户映射、活动任务、上传凭据路径、构建集成、下载入口和客户端版本，生成只读清单。
2. 使用现有在线备份与异盘校验流程，获得主库和附件清单一致的恢复点。同时补充上传队列、任务收据、制作任务文件、集成配置与密钥恢复依赖。
3. 将恢复点还原到全新演练目录，禁止让演练实例连接真实上传和发布目标。对比表记录数、ID、版本、外键、附件 SHA-256 和活动作业状态。
4. 在演练环境执行新增迁移与配置化启动；现有工作室保持原 ID 和功能行为。准备第二个空白工作室和独立测试连接，执行跨工作室验收。

当前主库备份成功不等于完整打包上传服务可以恢复。新增队列与任务文件属于独立状态源，需要明确各自一致性点；无法同时原子快照时，暂停相关任务派发，记录水位和未完成命令，再备份并通过回执在恢复后对账。

### 11 2 灰度接入

先部署新入口与控制目录，不改变原工作室的数据位置。将现有账号注册为工作室 A，验证原功能和正式身份映射；再创建空白工作室 B，只启用 QA 基础模块。B 通过隔离验收后，逐项开通打包、已有包上传、单次流水线，最后才启用自动触发。

切换窗口停止新增打包派发和对外发布，等待运行中任务到安全点；同时短时限制可能影响迁移一致性的业务写入。记录备份水位和路由版本，按实例切换并进行读回。不强行关闭日常客户端，也不删除工作区、历史附件或未同步草稿。

### 11 3 旧客户端兼容

旧入口和旧客户端只能绑定现有工作室 A，不提供隐式跨工作室能力。服务器按最低客户端版本决定是否允许登录和写入；兼容期结束前推动正常自更新或用户重启。多工作室身份、能力和队列字段优先做增量契约变更，避免全员同时断开。

现有姓名登录如需短期保留，应限制在明确的旧工作室与受控网络，并给出退场日期；在新的外部入口关闭该方式。不能用“仍在局域网”作为新工作室身份隔离的长期替代。

### 11 4 回滚

为代码、配置、实例路由和数据库迁移分别定义回滚方式。新 schema 尽量采用兼容扩展，先验证旧程序能否读写再允许安装包回退。新版本已经产生新业务记录后，不能直接用旧数据库覆盖，以免丢失他人的新写入。

某工作室失败时，优先只暂停该实例的新操作，回退其应用与配置，保留故障库和任务证据。确需数据库恢复时，在新目录恢复并对账，核对恢复点之后的新写入和外部发布，再切换该工作室路由。禁止为了恢复 B 而回滚 A 的数据。

外部平台发布通常不能随本地数据库回滚。恢复后先读取外部版本与幂等回执，已发布任务不得重新创建版本或重复推送。恢复演练必须覆盖这一情形。

## 12 运维与资源要求

按工作室监控 API 错误率、业务请求耗时、队列等待、执行耗时、磁盘与附件增长、上传带宽、失败重试、备份新鲜度和恢复结果。指标标签使用内部 ID，工作室用户仅查看自身指标。主机级故障由平台运维查看。

资源起点可设为每工作室 1 个活动构建和 1 个活动上传，但这是调度试点值，不是本机容量结论。先测当前工作室基线，再增加第二个工作室负载，测量数据库等待、API p95、磁盘响应和实际构建时长，据此决定 VM 内存、并发和带宽限制。

备份建议仍以 15 分钟作为业务库恢复点目标，扩展到每工作室验证。RPO 是可接受的数据丢失时间，RTO 是恢复服务耗时；文件、队列、配置与密钥也必须满足各自恢复承诺。可暂以单工作室恢复 60 分钟为演练目标，实测前不作为对外保证。

仅采用每工作室独立实例不需要立即切换 PostgreSQL。若需要多节点 API、高并发写入或更复杂跨实例管理，再评估 PostgreSQL。共享库采用行级策略时，还需注意表所有者和特权角色可绕过部分行安全规则，应用不能用特权账号处理普通租户请求。[PostgreSQL 行安全策略](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

工作室退出时，先停止新任务和自动触发，撤销访问与外部凭据，保留原任务和审计，按约定导出业务数据、附件及产物清单。停用不等于物理删除；保留期限和实际清理需单独确定，并覆盖在线文件、备份与客户端未同步草稿。单个工作室导出不得包含其他工作室数据或平台级密钥。

## 14 验收清单

验收建立 A、B 两个工作室，使用相同显示名、项目短编号、Bug 短编号和外部构建号制造冲突场景。同时创建仅属于 A、仅属于 B、同时属于两者以及已撤销的用户身份。以下用例为上线前必测；本次只编写方案，没有执行这些未来用例。

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| T01 | A 用户读取或修改 B 的 Bug ID | 拒绝且无 B 元数据、无业务写入 |
| T02 | 枚举附件、缩略图、Poco、日志和产物 URL | 下载均校验归属，旧链接和缓存不跨工作室 |
| T03 | A 与 B 同名用户登录和姓名认领 | 身份映射明确，无自动串号或跨工作室合并 |
| T04 | 伪造工作室头、项目 ID 或直连下游端口 | 路由与实例均拒绝绕过 |
| T05 | 切换时慢请求返回、后台轮询完成 | 新页面不会显示旧工作室记录 |
| T06 | 两个标签页分别在 A 与 B 写入 | 各自命令保持原页面工作室 |
| T07 | 同幂等键重复提交或异工作室提交 | 本作用域正确重放，互不覆盖 |
| T08 | 上传列表、打包链、日志和队列位置 | 只返回本工作室授权记录 |
| T09 | 相同渠道不同目标与相同真实外部目标 | 前者可按容量并行，后者互斥防覆盖 |
| T10 | 禁用模块后直接调用 API MCP 和旧页面 | 新操作被拒绝，历史可读，人工 QA 可操作 |
| T11 | 排队和执行中撤销权限或修改凭据 | 派发与最终发布重查；暂停可解释，无错误账号发布 |
| T12 | A 大量排队、上传或磁盘临近额度 | B 获得执行机会；A 不耗尽全机保留空间 |
| T13 | Relay 或轻语失败及延迟回调 | 本地人工处理可完成，旧回调不覆盖人工事实 |
| T14 | 重启一个工作室 API 或上传调度器 | 原命令恢复，无重复上传；另一工作室数据正常 |
| T15 | 只恢复 B 的数据库与附件 | A 的记录、队列、目录和版本无变化 |
| T16 | 外部已发布但本地回执尚未保存时恢复 | 先对账外部，避免重复版本与重复发布 |
| T17 | Windows 通知点击与 MCP 短编号查询 | 进入原授权作用域，歧义查询拒绝 |
| T18 | Android 离线提交后切换或权限撤销 | 草稿保留并暂停，不能提交到另一工作室 |
| T19 | 客户端升级与回退 | 服务器配置、草稿、身份映射及恢复证据保留 |
| T20 | 新工作室空白开通与失败重试 | 无原工作室业务或凭据，重复开通无残留冲突 |

隔离门槛是上述跨工作室越权读取与写入为零，验证失败不能用页面隐藏代替修复。并发和性能指标应在 P0 根据真实负载确定；建议试点测量 B 在 A 满额负载下普通业务请求 p95 相对基线变化，超过约定比例时调整配额或拆分执行机。这里不虚构固定机器容量。

代码验证应覆盖存储不变量、认证与授权、契约兼容、上传恢复、构建适配和端到端场景。Windows 必须完成签名更新清单、下载哈希、打包 smoke、真实升级重启与配置保留验证；Android 若列入范围，需验证真实设备的登录、采集和离线恢复。

## 15 主要风险与控制措施

| 风险 | 影响 | 控制与上线门槛 |
| --- | --- | --- |
| 漏掉共享队列或旁路文件 | 上传、日志和附件跨工作室暴露 | 存储清单覆盖所有状态源；T02 T08 T15 |
| 姓名或旧调试身份沿用到外部入口 | 可冒用其他成员 | 正式身份验证、邀请、独立映射；T03 T04 |
| 固定 Jenkins 或最新 ZIP 被复用 | 打包错项目、上传错版本 | 配置适配器和不可变产物回执；T09 T16 |
| 模块仅在前端隐藏 | API MCP 与后台继续执行 | 服务端统一能力校验；T10 T11 |
| 权限缓存或切换响应滞后 | 已撤销成员继续操作、页面串数据 | 短时上下文、动作前重查、请求作废；T05 T06 |
| 同机资源耗尽 | 所有工作室变慢或失败 | 配额、公平调度、磁盘保留与执行 VM；T12 |
| 数据恢复遗漏集成与队列 | 恢复后任务丢失或重复发布 | 多状态源一致性清单、外部对账；T14 T16 |
| 每工作室单独分叉代码 | 修改和发布成本持续增加 | 同一代码产物、版本化配置和固定能力目录 |
| 自动化改变原人工流程 | 现有团队无法继续处理问题 | 保留人工接管和独立 QA 验收；T13 |

多工作室隔离应覆盖认证、查询、缓存、文件和资源使用，而非只在主表增加过滤。这与 OWASP 的多租户隔离建议一致；本方案的具体部署取舍来自当前项目结构。[OWASP 多租户安全指南](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)

## 16 开工前需要确定的产品选择

这些选择不影响本方案交付，但会改变实施范围。建议在 P0 用真实工作室案例确认并记录。

| 需要确定的内容 | 本文默认建议 | 改变后的影响 |
| --- | --- | --- |
| 工作室部署位置 | 初期共用本机入口，独立业务实例 | 独立外部部署需要远程升级与网络方案 |
| 成员能否加入多个工作室 | 可以，通过可验证身份映射 | 只允许单工作室可减少身份与切换范围 |
| 单次打包上传的含义 | 人工触发一次打包后上传 | 若指一次性临时账号或其他流程，应重新拆能力 |
| 打包与上传平台是否相同 | 首期复用现有适配器，目标独立 | 不同平台增加专门适配与验收 |
| 首批客户端 | 完整首期包含 Web Windows Android MCP | 只做 Web Windows 可先试点，但应限制旧端能力 |
| 谁能开启模块和配置目标 | 平台授权，工作室管理员配置 | 自助订阅和计费需要额外产品与运维能力 |
| 是否允许访问其他工作室源码 | 不允许，执行器按工作室隔离 | 可信共享构建池也必须单独评估秘密与进程边界 |
| 隔离的服务承诺 | 业务隔离和独立恢复，共享宿主机风险明确 | 硬件故障独立需新增主机与故障域 |

推荐先完成 P0，确认首批两个工作室的真实项目、身份与外部平台，再按 P1 至 P6 分段交付。先用空白工作室验证隔离，再开放构建上传；通过真实产物和恢复验收后，才增加自动触发和更高并发。
