## Delivered boundary

- Six independent npm workspaces exist: Web, API, Worker, Domain, Contracts,
  and Storage.
- The API is an independent Fastify process and exposes
  `GET /api/v1/health/live` with service version and a validated build SHA.
- The Worker is an independent polling process with abort and signal-aware
  shutdown. It does not require Relay to be online.
- The Web workspace builds a mobile-first React/Vite PWA application shell.
  Its Workbox policy precaches only the shell and excludes API, attachment,
  authentication, integration, and upload routes from navigation fallback and
  runtime caching.
- Domain vocabulary keeps acceptance and closure human-owned. Exported
  automation lists are frozen at runtime, and mutation attempts cannot add
  `closed` to Relay authority.
- Storage defines repository/unit-of-work/health/configuration ports without
  opening a database or pre-empting P1 migrations. Source and data directories
  cannot contain one another; a separate drive is accepted.
- The repository contains no runtime/data/auth/state/synchronization dependency
  on Qingyu and no embedded Relay source/runtime path.

## Actual process start, health, stop, and restart

The compiled API was run twice on `127.0.0.1:4320` with build SHA
`0123456789abcdef0123456789abcdef01234567`:

1. PID `20204` started; a separate PowerShell process received HTTP 200 and the
   exact service/version/build fields. Ctrl+C produced an API log with
   `signal=SIGINT` and `stopping Relay QA Hub API`.
2. PID `16920` then bound the same port; the second independent health request
   again returned HTTP 200 with the same provenance. Ctrl+C again reached the
   SIGINT shutdown handler.
3. A final request after shutdown failed as expected and reported
   `port-closed-after-stop`.

The PTY host reports exit code 1 when Ctrl+C interrupts its PowerShell wrapper;
that wrapper code is not represented as the API exit code. Graceful Fastify
close is separately executable in the API test (listen, health, idempotent
`stop()`, and new-instance restart). The Windows E2E `child.kill()` proves
process restart only and is not misrepresented as graceful service shutdown.
Windows service-control behavior remains a P10 requirement.
