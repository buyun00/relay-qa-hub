## Scope and method

Only the production integration, backup and archive roots already named in `production-inventory.md/json` were enumerated. Roots and ancestors were checked with `lstat` and canonical-path comparison; traversal skipped links and did not follow any. The integration tree had no encountered links or enumeration errors. Main-database attachment and staging trees under the archive root were deliberately pruned; their binary contents are not component state inventories.

No SQLite connection was opened, no checkpoint was issued, and no production file was copied or modified. No process, listener, client or external service was operated. `auth.json`, Qingyu ciphertext, people configuration, logs and ZIP contents were not read. Exactly 25 known job/state/receipt/chain/batch JSON files were parsed to retain allowlisted status and binding-presence fields; user text, URLs, account details and credential fields were not recorded. Each selected file had the same size and mtime across its read. That is a per-file observation, **not** a cross-file consistency point.

## Pause and migration coverage

Legacy source binds these locations at `main.ts:408–415`, `increment-upload.ts:102,163–186`, `uploader-host.ts:200–221,555–562`, and `production-tasks.ts:147–163,268–298`. Legacy `ProductionTasks` resumes loaded batches after construction (`production-tasks.ts:139–142`), and legacy code does not recognize the import hold. The old Qingyu file/key dependency is at `main.ts:221–224,396–397`; replacing the encryption secret would not establish a valid restore.

Current `main.ts:339–344,441` uses the isolated project runtime and disconnects the old singleton registrations (`app.ts:2697–2734`). Current snapshots live at `components\projects\<project>\components\<key>\versions\<version>\configuration.json`; loading requires matching project/key/version (`project-components-runtime.ts:210–260`). Upload state is below the version directory, Relay state below its `production` child, and Qingyu state is `qingyu.encrypted.json` with an explicit credential reference. The runtime also owns `components\runtime.sqlite`. Existing legacy files cannot simply be placed there and become correctly scoped history.

The first upgrade of an unscoped upload queue adds `projectId=''` and `componentVersion=0`, and changes queued/dispatching commands to paused with `PROJECT_MIGRATION_REVIEW_REQUIRED` (`increment-upload.ts:114–123`). This retains records for review; it does not determine their project/version. Project-filtered reads subsequently require an explicit scope (`increment-upload.ts:163–168`). The legacy jobs and chains observed here would also fail the new binding checks without a deliberate mapping.

The current runtime checks execution hold for enabled operations, ticks, dispatch and resume; its outbox pump does not claim while held (`project-components-runtime.ts:275,848–860,1305,1367–1371`). The storage worker independently refuses claims and Relay attempt/dispatch/continue operations (`packages/storage/src/sqlite-worker-entry.ts:323–333`). A valid release requires marker version 1, `state=released`, actor, timestamp and reason; malformed/unreadable markers remain held. A missing marker is not held (`packages/storage/src/import-execution-hold.ts:4–24`). Components with no configuration default off (`project-management-store.ts:298–307`).

These guards prevent covered new execution; they do not import legacy directories, recover credentials, kill already running legacy subprocesses, or retroactively prove that a separately running old program honored the hold.
