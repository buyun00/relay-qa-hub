## Code 21 Relay controls and upgrade retention

`ComponentTaskScreen` now routes Relay to the dedicated native `RelayProductionScreen`. Its default page reads local `production/batches`; separate tabs read project `production/outbox` and, only when the component is ready, remote `production/tasks`. Local history remains available with the component off. Batch and outbox records display their actual original `componentVersion`; an unmapped remote task explicitly leaves version resolution to the server rather than claiming the current configuration is proven historical provenance.

Paused outbox entries use `POST production/outbox/:id/resume`; paused/failed local batches use `POST production/batches/:id/retry`. Both send the established empty `{}` body with the immutable token/project header. These APIs have no caller-supplied version/CAS fields: the server binds the stored project/version, enforces original batch owner where applicable, component enablement and import hold. Android does not invent unsupported parameters or automatically retry a rejected operation. A successful queue receipt is displayed as a request processed with final execution still requiring readback.

Remote continue/cancel/retry/reopen/finish remain available. Merge first reads the selected task detail, then displays an explicit confirmation checkbox/dialog naming that task and its fresh `updatedAt`. Only confirming submits `kind:action`, the same `taskId`, `expectedUpdatedAt` and `confirmMerge:true`; cancelling submits nothing. The UI explains that merge does not imply Bug acceptance closure. `RelayOperationsTest` adds ten bounded fixture cases for scope, old-version history, paused projections, empty resume bodies, action timestamps, merge confirmation, unknown fields, invalid IDs and intercepted native HTTP headers/body. The interceptor throws before network access; no external executor is used by these tests.
