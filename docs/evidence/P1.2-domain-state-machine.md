## Domain authority and workflow invariants

The pure Domain tests prove, among other rules:

- every actor is a current same-account/same-project member with the exact
  operation capability; assignees and verifiers are resolved from current
  scoped facts rather than trusted command labels;
- only one active RepairAttempt and one compatible active Verification can be
  represented, and the active Attempt must be the highest eligible sequence;
- duplicate canonical Bugs are same-project, non-self, fully resolved, and
  acyclic;
- delivery freezes the BuildRequirement decision, delivery version, commit or
  no-code evidence, and immutable audit relation;
- manifest Build linking requires the exact delivered commit in a ready Build;
  release-manager override additionally requires a reason-bound authority fact
  matching account, project, actor, capability, and reason;
- S0/S1 always require repairer/verifier separation, project policy may add
  severities, and the policy is re-evaluated both when Verification is created
  and when its result is recorded;
- only the assigned human verifier can pass/fail/block a started Verification;
  pass closes the Bug, fail preserves history and replans, and blocked clears
  only the active Verification pointer;
- a closed Bug reopens only from a post-closure occurrence on a strictly later
  server-ranked Build in the accepted Build lineage; no-Build closures cannot
  acquire a Build baseline after the fact;
- long legal aggregate truth is preserved while Event text is bounded and
  credential-like material is replaced with `[REDACTED]`.

## Contract semantic erratum

The frozen implementation plan requires S0/S1 separation plus any project-
configured severities. The 1.1.0 evaluator already consumed an exact
assignee/verifier-bound `separationOfDutiesFact`, but also contained a second
unconditional inequality that incorrectly rejected policy-authorized S2+
self-verification.

The reviewed erratum removes only those two redundant inequalities. Exact fact
identity and `passed === true` remain mandatory. Validator scenarios now prove
both create/result acceptance with an exact true policy fact and rejection with
a false or mismatched fact. OpenAPI, schemas, the 1.0.0 baseline, and all other
1.1.0 canonical hashes remain unchanged. The strict 1.1.0 baseline was updated
only for the evaluator, validator, and `frozenAt` values.

## Defensive SQLite migration 3

The forward migration binds workflow DML to current scoped principals, exact
typed Events, immutable relation facts, and forward one-version CAS:

- Bug state changes and same-state pointer changes require their exact typed
  Event and relation. Arbitrary repair/Verification pointer swaps, closed time
  rewrites, reopen-count rewrites, and duplicate repoints are rejected.
- RepairAttempts must begin as neutral planned version-one facts. Start,
  failure, supersede, delivery, and verification failure have exact allowed
  transitions; delivery evidence is immutable.
- Verifications must begin requested/version one for the exact delivered
  Attempt and assigned human. Result DML is bound to the current verifier and
  exact Event.
- Accounts, Projects, Users, Memberships, and roles must all still be active at
  the state-changing DML boundary.
- Duplicate chains are recursively cycle-free. Build lineage entries are
  same-scope, contiguous, append-only, and immutable. Each accepted
  `occurrence.appended` Event has one current-reporter Occurrence witness and,
  when a ranked Build is present, one immutable server-ranked lineage fact.
  The reverse bare-Occurrence-to-Event completion constraint is deferred to
  the P2.3/P3.3 UnitOfWork and recorded in `PROGRESS.md` technical debt.
- Human closure produces one immutable acceptance fact only after the exact
  passed Verification and Build/no-Build proof. Direct closure-fact inserts are
  rejected.
- Equal/older Build occurrences and any occurrence after a no-Build closure
  cannot reopen a Bug. A strictly newer same-lineage occurrence remains a
  positive path.

Event payloads are bounded to 4 KiB, restricted to the approved scalar key set,
and scanned across every text scalar. Raw authorization, bearer, credential,
secret, token, password, private-key, and single-backslash Windows-path values
are rejected regardless of which allowed key carries them; `[REDACTED]` is the
only explicit sensitive-text placeholder. Decision and override aggregate
truth may retain a private Windows path while their typed Event projection is
redacted.
